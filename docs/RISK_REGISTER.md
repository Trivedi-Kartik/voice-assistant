# Risk Register (Phase 0)

Risks, not debt items (see `TECH_DEBT.md` for concrete fixable items). Rated Likelihood × Impact, both Low/Medium/High, informal.

| # | Risk | Likelihood | Impact | Notes / mitigation direction |
|---|---|---|---|---|
| 1 | **Mandatory external API dependency contradicts the master doc's non-negotiable "no mandatory paid/cloud API" requirement.** The entire current product — STT, tool-calling LLM, vision — runs through Groq. Groq's free tier is genuinely free today, but it is still a *mandatory cloud dependency*: the app cannot function at all without network access and a working Groq account/key. | Certain (already true) | High (architectural, not incidental) | This is the central tension the whole roadmap has to resolve. Do not attempt to resolve it by ripping out Groq immediately — see `TARGET_ARCHITECTURE.md`'s model-router phasing. The near-term mitigation is the router abstraction (additive), not a local-model rewrite (risky, large, uncertain hardware fit). |
| 2 | **Groq's model catalog changes without notice and has already broken production three times** (chat model decommissioned once; vision model swapped twice, the second swap happening live during this very audit). | High (recurring, not hypothetical) | High (silent, total feature failure — not a graceful degradation) | Needs either a startup self-check against Groq's `/v1/models` endpoint, or a config-driven (not hardcoded) model name with an alerting path, before the next inevitable swap. See `TECH_DEBT.md` #7. |
| 3 | **Computer-use automation's accuracy ceiling is set by a free vision model with no measured success rate.** Misclicks are disclosed to users as an accepted trade-off, but there is no evaluation harness (master doc Phase 12) measuring how often this actually happens, so "accepted trade-off" is currently a guess, not a number. | High (inherent to the model choice) | Medium (real-world consequence is a wrong click, not data loss — but user trust erodes fast if this isn't tracked) | Needs at minimum a manual eval set (even 20-30 real tasks) before this capability is expanded or marketed further. |
| 4 | **Computer-use can execute real, hard-to-reverse actions** (a real purchase click, a real sent message) if the vision model mis-classifies a step's risk as `"low"` when it should be `"high"`. The risk classification itself comes from the same free, occasionally-wrong vision model deciding the click in the first place — there is no independent, deterministic backstop checking *that* specific judgment. | Medium | High (real-world, irreversible action taken without the confirmation gate that was specifically built to prevent this) | Worth a deterministic keyword/heuristic backstop (e.g. always treat any click near text like "buy," "pay," "send," "delete," "confirm order" as high-risk regardless of the model's own classification) layered on top of the model's judgment, not replacing it. |
| 5 | **In-memory-only per-user lock silently stops providing any protection if the server ever scales beyond one process.** No error, no warning — it would just silently allow concurrent turns per user, double-spending shared Groq quota and potentially interleaving history writes. | Low today (single process is the current, deliberate deployment shape) | High if it ever happens without this being remembered | Should be called out explicitly as a blocking prerequisite the day horizontal scaling is ever considered, not rediscovered live. |
| 6 | **No rate limiting on `/auth/signup`/`/auth/login`** — a real credential-stuffing / brute-force surface, already self-acknowledged in `docs/ARCHITECTURE.md` as deliberately deferred. | Medium (this is a live, internet-reachable production endpoint) | Medium (account takeover risk, not infrastructure risk — bcrypt's own cost factor is the only current friction) | Cheap to add (a standard rate-limit middleware on two routes); worth doing well before any broader user growth, independent of any architecture phase. |
| 7 | **No password-reset flow at all.** A user who forgets their password has no self-service recovery path. | Medium (will happen as soon as real growth begins) | Low-Medium (support burden / user lockout, not a security hole) | Needs an email-sending capability the product doesn't have yet (no email integration exists anywhere) — this is a real, non-trivial new capability, not a quick fix. |
| 8 | **Zero automated test coverage means every refactor (especially the `ws/session.ts` extraction Phase 1 requires) risks silent regressions in exactly the stateful, multi-turn logic that's hardest to eyeball-verify** (the three confirmation state machines). | High (structural, guaranteed to matter the moment Phase 1 starts) | High (a regression here breaks the core voice loop for every user) | This is why `IMPLEMENTATION_ROADMAP.md`'s Phase 1 slice must lead with characterization/regression tests for the current confirmation behavior *before* extracting anything, not after. |
| 9 | **`@xenova/transformers`'s model weights and its transitive `onnxruntime-node` native binary are both runtime-fetched/loaded, not vendored** — their exact licenses were not independently verified in this audit (only the npm package's own license is visible from `package.json`; the Hugging Face model card and the ONNX Runtime binary's license are separate, external artifacts). | Low (unlikely to actually be a problem, given both are well-known, permissively-licensed-in-practice components) | Medium if wrong (could affect redistribution terms of a packaged build that bundles cached model weights) | Needs an explicit, independent license check of the actual `Xenova/all-MiniLM-L6-v2` model card and `onnxruntime-node`'s license before this is marked resolved — see `dependency-registry.md`. |
| 10 | **No code signing on the Windows installer** — SmartScreen warns every new user on first run. | Certain (already happening) | Low today (accepted for invited testers), High if distribution ever broadens | Explicitly accepted, documented, and appropriate for the current phase — re-flagged here only so it doesn't get silently forgotten before any wider release. |
| 11 | **Local-model support (master doc Phase 3) has an unverified hardware-fit assumption.** Running a 27B-class model locally inside an Electron app on a typical user's laptop is a real RAM/VRAM question this audit found no evidence has been tested or even scoped. | Medium (easy to discover this is infeasible on typical hardware only after significant engineering investment) | High (a whole phase's premise could be wrong) | **Resolved with a concrete plan, not an open question** (see ADR 0001 decision 2): before any adapter code, run the smallest viable quantized model against `llama.cpp` on the two real machines already used for testing throughout this project (Windows laptop, Ubuntu Linux laptop) and measure real tokens/sec and memory footprint. That result is the gate for Phase 3b — no separate hardware survey needed. |
| 12 | **AppImage's Chromium-sandbox limitation on Linux is structural and confirmed unfixable in-app** (three different in-app fixes were tried and confirmed not to work, per `docs/SETUP.md`'s own account). | Certain (already true, already documented) | Medium (real friction for every Linux tester today, terminal launch required) | The only real fix is a `.deb`/`.rpm` packaging target instead of/alongside AppImage — not an application-code fix. Worth scoping as its own small slice whenever Linux distribution needs to get easier, independent of the main roadmap. |
| 13 | **No macOS support, and it isn't tracked as an intentional limitation anywhere in the docs** (unlike Wayland, AppImage sandboxing, or wake-word, which are all explicitly documented deferrals). | Certain (already true) | Low today (if genuinely no macOS users exist yet), Medium if that assumption is wrong | Cheap to fix by just adding it to `docs/ARCHITECTURE.md`'s "Current limitations (intentional)" list, if it is in fact intentional — otherwise it's a silent, undocumented gap. |
