# Technical Debt Register (Phase 0)

Concrete, file-cited debt items — not a general architecture critique (see `SYSTEM_AUDIT.md` for that). Each item has an owner subsystem and a rough cost-to-fix so `IMPLEMENTATION_ROADMAP.md` can sequence sensibly.

| # | Item | Where | Cost to fix | Notes |
|---|---|---|---|---|
| 1 | Zero automated tests anywhere in the repo | whole codebase | High (ongoing) | No `*.test.ts`/`*.spec.ts` files exist; no test runner configured; no `test` script in either `package.json`. Every "real bug" documented in `CHANGELOG.md` was found by a human manually running the app. This is the single largest debt item and blocks safely refactoring `ws/session.ts` (see `SYSTEM_AUDIT.md` §2). |
| 2 | No CI pipeline | whole repo | Medium | No `.github/workflows/` (confirmed absent). Typecheck/build could be gated on every push today with near-zero design work — this is cheap, high-value debt to pay down early, independent of any architecture phase. |
| 3 | No lint configuration despite lint-shaped comments in source | whole repo | Low | Multiple files contain `eslint-disable-next-line` comments (e.g. `server/src/tools/schemas.ts`) referencing a linter that isn't configured anywhere (no `.eslintrc*`/`eslint.config.*` found). These comments are currently dead weight — either add ESLint or remove the comments. |
| 4 | Hand-duplicated cross-package contracts | `server/src/tools/toolNames.ts` ↔ `agent/src/shared/toolContract.ts`; `server/src/i18n/languages.ts` ↔ `agent/src/renderer/i18n/languages.ts`; `server/src/protocol.ts` ↔ `agent/src/shared/protocol.ts` | Medium | Caught today only by boot-time assertions on each side. Has grown past the original "3 string literals" justification (`toolNames.ts`'s own comment). Not urgent — the assertions work — but will get worse with every new tool/message type added by hand in both places. |
| 5 | `ws/session.ts` god-object | `server/src/ws/session.ts` (~610 lines) | High | Owns turn orchestration, STT, memory, prompt construction, three separate confirmation state machines, rate-limit/lock, and persistence. Blocks Phase 1 (agent kernel) until extracted. See `SYSTEM_AUDIT.md` §2 and `TARGET_ARCHITECTURE.md`. |
| 6 | Direct Groq SDK construction at every model call site | `server/src/llm.ts`, `stt.ts`, `vision.ts`, `automation/vision.ts` | Medium | No adapter/router interface exists; each file builds its own `new Groq(...)`. Blocks any model-router work (master doc Phase 3) until extracted — should be a pure interface-extraction with the existing Groq behavior becoming the first adapter, zero behavior change. |
| 7 | Vision-model name is a bare string constant, no fallback | `server/src/vision.ts`, `server/src/automation/vision.ts` | Low (immediate), Medium (durable fix) | Already caused a live production outage during this very audit period (`qwen/qwen3.6-27b` → 404, fixed to `qwen/qwen3.8-27b`). This is the *third* time a Groq model name has changed out from under this codebase (chat model and vision model each once before). A durable fix (config-driven model name, or a startup self-check against `/v1/models`) is worth doing before the next inevitable swap, not after. |
| 8 | `recordUsage()` always called with an empty delta | `server/src/rateLimit.ts`, call sites in `ws/session.ts` | Low | `UsageEvent.groqSttSeconds`/`groqTokensIn`/`groqTokensOut` columns exist and are never populated by any call site found in this audit — only `turnCount` increments meaningfully. Either wire the real values through or remove the unused columns/fields; the current half-wired state misleads anyone reading the schema. |
| 9 | Unbounded renderer conversation array | `agent/src/renderer/state/store.ts` (`turns`) | Low | `pushTurn` appends forever, no cap, no virtualization in `ConversationView.tsx`. Not yet a measured problem, but no guard exists either. |
| 10 | `ROADMAP.md`'s "Next" sub-lists are stale relative to shipped code | `ROADMAP.md` (repo root) | Low | Its own Linux-compatibility "Next" list still shows `add_custom_app` on Linux and Linux packaging as not-done, but both exist and work in the current code (`addCustomApp.linux.ts`, `electron-builder.yml`'s `linux:` block). Documentation drift, not a code problem — cheap to fix, worth fixing before it misleads a future contributor. |
| 11 | `docs/SETUP.md`'s prerequisites section is stale | `docs/SETUP.md` | Low | States "Windows 10/11 for running the client (tool implementations... are Windows-specific in v1)" — no longer true; Linux implementations exist and a working AppImage target ships. Same category as #10. |
| 12 | Duplicate/overlapping model-call shape between screenshot description and computer-use decisions | `server/src/vision.ts` (`describeImage`) vs `server/src/automation/vision.ts` (`decideNextAction`) | Low | Two independent "call a Groq vision model with an image_url block" implementations, kept in sync only by a code comment ("kept in sync — see that file's comment"), not by shared code. Small today; worth consolidating before a third vision call site appears. |
| 13 | No macOS support anywhere, and no doc says so explicitly | whole `agent/` package | Medium (if macOS is ever in scope) | No `.mac.ts` variant exists for any platform-specific module; no macOS packaging target in `electron-builder.yml`. Not currently listed as a known limitation in `docs/ARCHITECTURE.md`'s "Current limitations (intentional)" section — should be, if it's intentional, or tracked as a gap if not. |
| 14 | Computer-use automation shipped with a real, already-fixed coordinate-scaling bug class | `agent/src/main/tools/computerUse/`, `automation/` | Already fixed once; risk of recurrence | Documented in `RISK_REGISTER.md` as an ongoing risk category (any future change to screenshot resize logic must re-verify the scale factor is still threaded through to input execution) rather than a one-time fixed bug. |
